# 硬件覆盖

本手册里每一条逐 bit 一致的结论，都只在证明它的那套软件栈上成立。换了 GPU、驱动或库之后，
[回归套件](regression.md)会告诉你哪些结论仍然成立。本页讲软件栈的哪些属性会改变结果，
为什么不应指望两代 GPU 的结果一致，以及怎样验收新硬件。

## 思路

假设在 GPU 上把 4,096 个数加起来。SM 多的 GPU 上，库可能把它们分成很多份部分和；SM 少的 GPU 上，
可能只分成几份。不同的分法在不同的地方舍入，所以即使源码和输入完全相同，总和的最后一个 bit
也可能不同。规则是：**凡是决定一次归约怎样切分、按什么顺序、在哪里舍入的东西，都是软件栈的
一部分；逐 bit 一致的结果只属于那套软件栈。** 这和 batch-invariant 背后是同一条原则，只是往上
提了一层：那里是 batch 决定了用哪个 kernel，这里是机器决定的。

## 软件栈的哪些属性会改变结果

| 属性 | 它怎样改变结果 |
|---|---|
| 架构 | 每一代 GPU 都有自己的矩阵指令，没有任何保证说各代的累加顺序或中间精度相同。库为每种架构提供不同的 kernel，有些 kernel 和数值格式只在较新的一代上才有。Triton 按架构分别编译，同一份源码会变成不同的机器码。 |
| SM 数量 | 库根据 SM 数量选择 kernel、tile 和 split-K，归约 kernel 和随机数 kernel 也根据它决定 grid 大小。所以同一架构、SM 数量不同的两种 GPU，结果可能不一致。 |
| 驱动 | 在测过的扫描里，库相同、驱动版本不同的两组机器给出了逐 bit 一致的结果。但驱动仍然算在基线的键里，因为 CUDA 有一部分是随驱动一起提供的。 |
| CUDA 构建与库 | cuBLAS、cuDNN 和 NCCL 每个版本选用的 kernel、算法和协议都可能不同；torch 也可能改变某个算子用哪个后端（例如 SDPA）。 |
| 互连 | NCCL 根据拓扑和消息大小选择算法（Ring 或 Tree）和协议，而算法决定了集合通信的求和顺序。 |

能延续到别的硬件上的，是归约顺序写在源码里、不依赖设备的 kernel。手册里的 Triton kernel 在
同一代、SM 数量相差很大的两种 GPU 上给出了逐 bit 一致的结果，而原生 GEMM、大规模归约和随机数流
做不到。这些 kernel 在另一种架构上能否逐 bit 一致，**未测试**。实测：见
[测得的覆盖范围](../../suite/COVERAGE.md#same-bits-on-two-gpus-of-one-generation)。

不同代的 GPU 之间，不要指望逐 bit 一致。一个已报告的例子：DeepSeek-V3 技术报告
（arXiv 2412.19437）提到，较新 tensor core 上的 FP8 GEMM 累加时只保留有限的精度，所以它每隔
固定的间隔把部分和提升到 CUDA core 上累加。因此要在每套软件栈上验证每个不变性级别（L1–L5）；
跨代逐 bit 一致，只有测过之后才能声明。

## 怎样验收新硬件

你要弄清哪些结论在新软件栈上仍然成立，哪些原生算子的行为不同了。新软件栈的基线经过审查后
已经提交，而且每一处差别要么作为这套软件栈特有的原生结果记录下来，要么作为一个发现报告出来，
就算完成了。

1. **以 full 模式运行回归套件**，加上 `--vs-committed`，按
   [回归一页"新硬件"一节](regression.md#new-hardware)的说明操作
   （[tools/bi_suite.py](../../tools/bi_suite.py)）。
2. **运行 SDC 扫描**，加上 `--cross-group-info`，对照已提交的 golden 文件
   （[tools/sdc_scan.py](../../tools/sdc_scan.py)）。它会列出哪些算子族和以前测过的软件栈
   逐 bit 一致，这只作为参考信息。
3. **给差别分类。**每一项失败的必需检查都是一个发现，要报告出来。原来记录在案的原生失败如果现在通过了，就是
   一处变化，要记到它的主题页上，并写明新的软件栈。
4. **记录基线**，并把这套软件栈加到[测得的覆盖范围](../../suite/COVERAGE.md#what-was-measured)里。

| 选项 | 能得到什么 | 代价等级 | 什么时候选 |
|---|---|---|---|
| 套件，quick 模式 | 在缩小的尺寸下检查每一条结论 | 小 | 先看一眼，或者只是小的库更新 |
| 套件，full 模式加 `--vs-committed` | 用写页面时的尺寸检查，并列出哪些结果变了 | 大 | 新 GPU、新架构，或者发布之前 |
| SDC 扫描，跨组比较 | 哪些算子族和已测的软件栈逐 bit 一致 | 小 | 新 GPU，用来看哪些东西可以跨机器比较 |

## 哪些还没在其他硬件上测过

这里要把两件事分开。据 OpGuard 的作者报告
（[OpGuard 论文](https://www.usenix.org/conference/osdi26/presentation/zhou-ziming)），
**OpGuard 本身**（采集、fingerprint、找首个分歧点的比较）已经在下面这些平台上用于生产环境的
LLM 训练。
**本手册自己的测量**（batch-invariant kernel 和各种修复、固定的集合通信树、引擎一致性的搭建）
都来自同一代 GPU，节点内走 PCIe，两个节点之间走普通以太网。引擎一致性的搭建还在另一代 GPU 上
用引擎自己的 kernel 证明过，见 verl × FSDP2 × vLLM 案例
（[报告](../../examples/verl_fsdp2_vllm/REPORT.md)）；本手册自己的 kernel 仍然只在一代 GPU 上
测过。这些测量在下面这些平台上尚未证明：

| 范围 | OpGuard | 本手册的 kernel、修复和搭建 |
|---|---|---|
| 其他 GPU 架构、其他加速器 | 已用于生产（据报告） | 未测试 |
| FP8 tensor-core GEMM 及其精度提升间隔、NVFP4 | 已用于生产（据报告） | 未测试（FP8 scale 是模拟的） |
| 其他 GPU 架构上较新的注意力 kernel（FlashAttention 3、FlashMLA、FlashInfer） | 已用于生产（据报告） | 未测试 |
| NVLink、NVSwitch、NVLS；RDMA、InfiniBand、RoCE | 已用于生产（据报告） | 未测试；固定的集合通信树只在 PCIe 和以太网上证明过 |
| 两个以上的节点 | 已用于生产（据报告） | 未测试；在两个节点上成立的固定 Tree，在三个节点上未必成立 |
| 其他版本的 torch、Triton、NCCL 和 CUDA | 已用于生产（据报告） | 未测试，跨引擎案例里 vLLM 自带的软件栈，以及 verl × FSDP2 × vLLM 案例里 verl 和 vLLM 的软件栈除外 |

所以在这样的平台上，照常用 OpGuard 定位问题；但在依赖本手册的任何不变性结论之前，先用套件重新
验证。每个结果文件对应的具体软件栈见[测得的覆盖范围](../../suite/COVERAGE.md)。

## 可能出错的地方

!!! warning "以为结果会自动延续到新硬件上"
    新 GPU 看起来只是更快的旧 GPU，但它的库会选别的 kernel，所以没测就沿用的结论，在它上面
    可能是错的。依赖任何逐 bit 一致的结论之前，先跑一遍套件。

!!! warning "用原生算子跨机器比较"
    两种不同的机器跑原生 GEMM 或随机数 kernel，可能在没有任何 bug 的情况下结果不一致。跨机器
    比较时，只比较顺序写死在源码里的算子，或者让每台机器只和自己比较。

!!! warning "在新硬件上用容差把失败掩盖掉"
    必需检查在新硬件上失败，说明这种硬件或它的库有问题，这是一个发现。用容差把它藏起来，会让
    这套软件栈上之后的每一条结论都不可信。要把它报告出来。

## 小结

- 逐 bit 一致的结果只属于它的软件栈：架构、SM 数量、驱动、CUDA 构建、库和互连。
- 不要指望不同代的 GPU 逐 bit 一致；声明之前先测。
- 只有归约顺序写死在源码里的 kernel，才可能延续到别的硬件上。
- 用 full 模式的套件和 SDC 扫描验收新硬件，然后记录基线。
