# 怎样写一页 handbook

handbook 教三条工作流程：找到两次预训练从哪里开始分开（第 1 部分），
让 rollout 引擎和 trainer 一致（第 2 部分），让一个算子满足不变性（第 3 部分）。
第 0 部分讲三条流程共同依赖的概念。每一页是某条流程中的一步或一个概念。
实验是证据，放在报告里，不放在正文里。

## 读者是谁

懂 PyTorch、GPU 和 RL 训练的 ML 系统工程师，手上正有一个问题。
他读一页，是为了知道下一步做什么、为什么这样做。

## 一页的结构（d2l 的顺序）

1. **我们在哪里。** 一两句话，链接到上一步：读者现在手里有什么，还有什么不对。
   每部分的第一页说明整条流程要达到什么，并列出它的各个步骤。
2. **概念，先讲直觉。** 先用一个小例子或一张图讲清机制，再给规则：
   三个数按两种顺序相加；同一行在 batch 为 1 和 64 时；一个 decode 步对照一次 prefill。
   然后用一句话写出规则，并指出它是哪条通用原则的一个实例。
3. **这一步。** 按顺序写要做什么，用一个简短的编号列表。每一步是一句加粗的动作，后面跟两三句话：
   做什么、用哪个工具或 skill（附链接），以及怎样算做成了。只有在原因不显而易见时才写为什么。
   不要把每一步都拆成"目标 / 做法 / 成功标准"三栏：目标往往就是步骤名的重复，
   千篇一律的标签会让页面读起来像一张表格。多个选项用一张小表：选项、得到什么、代价等级、什么时候选。
4. **哪里会出错。** 坑用 `!!! warning` 提示框列出：一句原因，一句后果，一句该怎么做。
5. **小结。** 三到五条读者应当记住的要点。
6. **深入阅读。** 附测量结果的报告、代码、skill。

## 正文里不放什么

- **不放具体实验。** 不写 GPU 型号、驱动、库版本、模型尺寸、batch size 扫参、耗时、
  元素百分比、检查项的个数。这些放在 `examples/<name>/REPORT.md`。
  正文写一般规律（"行数变化时 cuBLAS 可能换一个 kernel，所以同一行在另一个 batch 里可能舍入不同"），
  并把报告作为证据链接过去（"实测：见报告"）。
- 不写 agent 是怎么做出来的，不写重试过程，不列逐个文件的清单。
- 解释性的句子里不放代码标识。工具名和 skill 名只出现在"这一步"和"深入阅读"里。

代价按等级写，不写数字："免费"、"小（百分之几）"、"中等（不到 2 倍）"、
"大（2 倍或更多）"，具体数字在报告里。
可以写出什么成立（逐 bit 一致、满足 L2 不变性），但要链接到证据，
并用平实的话写明在什么条件下得到（"在一种 GPU 上得到"、"在两个节点、最多 16 个 GPU 上得到"）。

## 句子

- 一段只讲一个意思，段首就说出来。
- 术语第一次出现时给出定义，或者链接到术语表；同一样东西在每一页都用同一个词。
- 能用一张图（Mermaid）或一张小表说清楚结构，就不要写一大段文字。
- 不用宣传性的词，不写"只需"，不要一连串的限定语。

## 自然的语言

像一位细心的工程师给同事讲解那样写，而不是把笔记压缩成摘要。每个标题和句子都读出声来；
如果读者需要"解码"才能看懂，就重写。

- **标题要短、要平实**，像书的目录条目：几个词的名词短语（英文大约不超过六个词，中文大约不超过十五个字），
  不写成句子，也不压缩成公式。其余的话留给这一页的开头一段。
  "LoRA：训练批次里一个适配器，服务批次里多个"和"LoRA：训练时只有一个 adapter，推理时一个 batch 混着多个 adapter"
  都改成"LoRA：多 adapter 混合 batch"；"换 TP 规模，结果仍逐 bit 一致（L5）"改成"任意 TP 规模（L5）"。
  小节标题也照此办理。
- **不写残句、不堆名词短语、不用一串冒号。** 用有主语、有动词的完整句子。
- **不要解说这一页，也不要哄着读者。** 不写"这一页带你走一遍""就像教科书……""值得慢慢读"
  "最容易忽略的地方""剩下的部分要回答"。直接写案例和结果；读者是同事，不是学生。
- **说清楚谁做了什么。** 写"引擎把共用同一个适配器的 token 分成一组"，不要写"引擎的适配器分组"。
- **一个概念只用一个词，并且只解释一次。** 同一个意思不要混用 "bits"、"位"、"比特"；用术语表里的词。
- **通用的小节名保持朴素**（"我们在哪里""思路""步骤"），但小节里的内容要连成通顺的段落，
  用"所以""因为""也就是说"这样的连接词。
- **中文按中文来写**：自然的语序，不套英文句法，不要"位都相同""两侧相遇的位置""以相同方式舍入"
  这类直译。改成"结果逐 bit 一致""在哪一步把两部分加起来""在同一个地方做舍入"。
  保留术语表规定的英文术语（rollout、trainer、kernel、logprob……），但要在它们周围用中文讲清楚。

### 中文术语：约定俗成的英文词不要硬译

中文 ML 系统圈子里习惯直接说英文的词，一律保留英文，不要翻成生造的中文：

| 保留英文 | 不要写成 |
|---|---|
| bit（"逐 bit 一致"） | 位、比特（"位都相同"） |
| batch、token、kernel、GEMM、tile、split-K | 批次、令牌、内核、通用矩阵乘 |
| prefill、decode、KV cache | 预填充、解码、键值缓存 |
| TP、DP、EP、PP、SP，以及 rank、shard | 张量并行规模下、秩 |
| rollout、trainer、logprob、staleness | 推演、训练器、对数概率、陈旧度 |
| torch.compile、CUDA graph、eager | 编译代码、CUDA 图、急切模式 |
| checkpoint、dtype、bf16、fp32 | 检查点、数据类型 |
| all-reduce、reduce-scatter、all-to-all | 全规约、规约散射 |
| LoRA、adapter、MoE、expert、top-k | 适配器、专家混合 |
| fingerprint、harness、skill、agent、SDC | 指纹（可在首次出现时括注"指纹"） |

这些词本身就是通用的中文表达：确定性、不变性、归约、舍入、算子、采样、前向、反向、梯度、
优化器、精度、并行度、训练、推理、对齐。

"job"不要写成"作业"，写"训练任务"或"任务"；"side"不要写成"侧/两侧"，写"rollout 端、trainer 端、两端"。

全书已经统一的几个写法：capture 一律写"采集"，只有 CUDA graph 的 capture 写"录制"；
probe、recipe、paged KV、capacity、speculative decoding 保留英文，不写"探针""配方""投机解码"；
bit-equal 统一写"逐 bit 一致"；选项表的表头统一用
"能得到什么""代价等级""什么时候选"。

改写示例：

| 机器翻译腔，或者太长 | 简短通顺的中文 |
|---|---|
| 并行度：每个 TP 大小下位都相同（L5） | 任意 TP 规模（L5） |
| 作业运行编译代码时 | torch.compile 与 CUDA graph |
| LoRA：训练时只有一个 adapter，推理时一个 batch 混着多个 adapter | LoRA：多 adapter 混合 batch |
| 让单侧不变：整个模型 | 整个模型的不变性（L1–L3） |

## 诚实

- 不要在措辞上削弱结果：逐 bit 一致就是逐 bit 一致；已知答案的演示就叫已知答案的演示；
  模拟出来的就说是模拟的。
- 没测过的内容要留在明处：如果它会改变读者的做法，就在正文写一行简短的"尚未证明"，
  完整列表放在待办事项里。

## 中文页

中文页按中文的写法来写，不要逐句翻译：章节、链接和代码与英文版相同；
语序用自然的中文；保留术语表规定的英文术语。句子要短。

## 完成前检查

- [ ] 页面开头说明读者在流程中的位置。
- [ ] 在给出任何规则之前，先用小例子讲清机制。
- [ ] 正文里没有硬件型号、版本、尺寸、耗时或百分比。
- [ ] 每个动作都写明了工具或 skill 和成功条件。
- [ ] 每个"什么成立"的结论都链接到证据。
- [ ] 中英两版的章节、链接和代码一致（`scripts/check_i18n.py`）。
- [ ] `mkdocs build --strict` 通过。
